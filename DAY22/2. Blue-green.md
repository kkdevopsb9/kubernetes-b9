In Kubernetes, **Blue-Green Deployment** means you run **two versions of the application at the same time**.

* **Blue** = current production version, for example `v1`
* **Green** = new version, for example `v2`
* A Kubernetes **Service** decides which version receives user traffic.
* After testing Green, you switch the Service selector from Blue to Green.
* If Green has a problem, rollback is very fast: point the Service back to Blue.

### Architecture

```text
                         Users
                           |
                           v
                  +----------------+
                  | Service        |
                  | app-service    |
                  +----------------+
                           |
                     selector:
                     version=blue
                           |
                           v
              +-------------------------+
              | BLUE Deployment         |
              | nginx:1.24              |
              | version: blue           |
              +-------------------------+

Meanwhile:

              +-------------------------+
              | GREEN Deployment        |
              | nginx:1.27              |
              | version: green          |
              +-------------------------+
```

Initially, users are accessing **Blue**.

## 1. Blue Deployment — Current Production

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: blue-deployment
spec:
  replicas: 3

  selector:
    matchLabels:
      app: webapp
      version: blue

  template:
    metadata:
      labels:
        app: webapp
        version: blue

    spec:
      containers:
        - name: nginx
          image: nginx:1.24
          ports:
            - containerPort: 80
```

Apply it:

```bash
kubectl apply -f blue-deployment.yaml
```

Check:

```bash
kubectl get deployments
kubectl get pods --show-labels
```

You may see:

```text
NAME                              READY   STATUS
blue-deployment-xxxx              1/1     Running
blue-deployment-yyyy              1/1     Running
blue-deployment-zzzz              1/1     Running
```

---

## 2. Create Service and Send Traffic to Blue

```yaml
apiVersion: v1
kind: Service
metadata:
  name: app-service

spec:
  type: NodePort

  selector:
    app: webapp
    version: blue

  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080
```

Important part:

```yaml
selector:
  app: webapp
  version: blue
```

So the Service sends traffic **only to Blue pods**.

Apply:

```bash
kubectl apply -f service.yaml
```

Check:

```bash
kubectl get svc
```

Test:

```bash
curl http://<NODE-IP>:30080
```

At this point:

```text
User
 |
 v
Service
 |
 | version=blue
 v
Blue v1
```

# 3. Deploy Green Version

Now assume developers released a new application version.

Blue:

```text
v1
```

Green:

```text
v2
```

Create another Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: green-deployment

spec:
  replicas: 3

  selector:
    matchLabels:
      app: webapp
      version: green

  template:
    metadata:
      labels:
        app: webapp
        version: green

    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
```

Apply:

```bash
kubectl apply -f green-deployment.yaml
```

Now:

```bash
kubectl get pods --show-labels
```

Example:

```text
blue-deployment-xxx     Running   app=webapp,version=blue
blue-deployment-yyy     Running   app=webapp,version=blue
blue-deployment-zzz     Running   app=webapp,version=blue

green-deployment-aaa    Running   app=webapp,version=green
green-deployment-bbb    Running   app=webapp,version=green
green-deployment-ccc    Running   app=webapp,version=green
```

Both versions are running.

But production traffic is still going to:

```text
version=blue
```

# 4. Test Green Before Production

You normally test Green separately.

For example, create a temporary Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: green-test-service

spec:
  type: NodePort

  selector:
    app: webapp
    version: green

  ports:
    - port: 80
      targetPort: 80
      nodePort: 30081
```

Apply:

```bash
kubectl apply -f green-test-service.yaml
```

Test:

```bash
curl http://<NODE-IP>:30081
```

Architecture now:

```text
                 Production Users
                       |
                       v
               app-service
                       |
                  version=blue
                       |
                       v
                     BLUE v1


                 Testing Team
                       |
                       v
            green-test-service
                       |
                 version=green
                       |
                       v
                     GREEN v2
```

If Green is working correctly, switch production.

---

# 5. Switch Traffic from Blue to Green

You don't need to delete Blue.

Simply change the production Service selector.

Current:

```yaml
selector:
  app: webapp
  version: blue
```

Change to:

```yaml
selector:
  app: webapp
  version: green
```

Complete Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: app-service

spec:
  type: NodePort

  selector:
    app: webapp
    version: green

  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080
```

Apply:

```bash
kubectl apply -f service.yaml
```

Now:

```text
User
 |
 v
Service
 |
 | version=green
 v
Green v2
```

Blue is still running but no longer receives production traffic.

---

# Faster Way to Switch

Instead of editing YAML, you can patch the Service.

Blue → Green:

```bash
kubectl patch service app-service \
  -p '{"spec":{"selector":{"app":"webapp","version":"green"}}}'
```

Check:

```bash
kubectl describe svc app-service
```

You should see:

```text
Selector:
app=webapp,version=green
```

Check endpoints:

```bash
kubectl get endpoints app-service
```

---

# 6. Rollback

Suppose users report an issue in Green.

You don't need to rebuild anything because Blue is still running.

Simply change:

```text
green
```

back to:

```text
blue
```

Command:

```bash
kubectl patch service app-service \
  -p '{"spec":{"selector":{"app":"webapp","version":"blue"}}}'
```

Traffic immediately returns to:

```text
Users
  |
  v
Service
  |
  | version=blue
  v
BLUE v1
```

This **fast rollback** is one of the biggest advantages of Blue-Green deployment.

## Complete Flow

```text
STEP 1

Users
  |
Service
  |
  v
BLUE v1

GREEN v2
(no production traffic)


STEP 2

Deploy and test Green

Users
  |
Service
  |
  v
BLUE v1

Testers
  |
Green Test Service
  |
  v
GREEN v2


STEP 3

Switch Service selector

Users
  |
Service
  |
  v
GREEN v2


BLUE v1 remains available for rollback


STEP 4 — If Green fails

Users
  |
Service
  |
  v
BLUE v1
```

### Interview explanation

You can explain it like this:

> **Blue-Green deployment is a release strategy where two identical environments are maintained. Blue represents the current production version and Green represents the new version. We deploy and validate the Green version without affecting production traffic. Once testing is successful, we change the Kubernetes Service selector from Blue to Green. If any issue occurs, we can quickly rollback by changing the selector back to Blue.**

One important difference from **RollingUpdate** is that Blue-Green keeps the old and new environments independently available during the release, which makes rollback very fast but requires more infrastructure/resources.
